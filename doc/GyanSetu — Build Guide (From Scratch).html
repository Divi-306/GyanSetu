GyanSetu — Build Guide (From Scratch)

A phased, checklist-driven guide to actually build GyanSetu, following the order and architecture from the workflow design doc. Each phase has: what you're building, exact setup/commands, files to create, and a "done when" test — don't move to the next phase until that test passes for real, on a real device/emulator with airplane mode toggled, not just in your head.

Total: 12 phases. Phases 1–8 are the non-negotiable core. 9–12 can compress if time runs short.

Phase 0 — Prerequisites & accounts (30 min)

  • Node.js LTS installed, npm or pnpm working
  • Expo CLI: npm install -g eas-cli (EAS not required for dev, but useful later)
  • Android Studio (emulator) or a physical Android phone with Expo Go, or Xcode/iOS simulator on Mac
  • PostgreSQL installed locally, or a free hosted instance (Neon, Supabase, Railway — any works for a hackathon)
  • A code editor with TypeScript support
  • Git repo initialized, .gitignore with node_modules, .env

Done when: you can run npx expo --version and connect to your Postgres instance with a client (psql, TablePlus, or Postgres extension in your editor).

Phase 1 — Project scaffolding (1–2 hrs)

1a. Mobile app

npx create-expo-app@latest gyansetu-app --template
cd gyansetu-app
npx expo install expo-router expo-sqlite expo-file-system expo-secure-store expo-network @react-native-community/netinfo
npm install zustand zod

Set up Expo Router file-based structure:

app/
  _layout.tsx
  index.tsx              # → redirects to splash or home based on auth state
  (auth)/login.tsx
  (auth)/signup.tsx
  (tabs)/_layout.tsx
  (tabs)/home.tsx
  (tabs)/courses/index.tsx
  (tabs)/courses/[id].tsx
  (tabs)/downloads.tsx
  (tabs)/scholarships.tsx
  (tabs)/career.tsx
  (tabs)/profile.tsx
  lesson/[id].tsx
  quiz/[id].tsx
  quiz/[id]/result.tsx

Create the base folders from the module architecture:

store/        (authStore.ts, connectivityStore.ts, downloadStore.ts, syncStore.ts)
db/           (schema.ts, client.ts, queries/)
services/     (storageManager.ts, syncEngine.ts, aiService.ts, downloadManager.ts)
components/   (OfflineBanner.tsx, SyncBadge.tsx, PackCard.tsx, CleanupModal.tsx)

Done when: npx expo start launches, and you can navigate between two placeholder screens (e.g. Home and Courses) using Expo Router.

1b. Backend

mkdir gyansetu-api && cd gyansetu-api
npm init -y
npm install express cors dotenv bcrypt jsonwebtoken zod pg
npm install -D typescript ts-node-dev @types/express @types/node
npx tsc --init

src/
  index.ts
  routes/ (auth.ts, courses.ts, packs.ts, sync.ts, ai.ts, scholarships.ts, career.ts)
  services/
  db/ (pool.ts, migrations/)
  middleware/ (auth.ts, validate.ts)

Done when: GET /health returns 200 { status: "ok" } from a running Express server, callable from your phone/emulator over your local network (same Wi-Fi, use your machine's LAN IP, not localhost).

1c. Database

Write raw SQL migrations (or use Prisma if you prefer — either is fine) for the tables in the workflow doc's data model (User, Course, Lesson, LearningPack, Quiz, QuizQuestion, QuizAttempt, StudentProgress, Note, SyncQueue, Scholarship, CareerRecommendation, AIKnowledgeChunk, StorageEvent).

Done when: all tables exist in Postgres and you can insert/select a test row in each from a SQL client.

Phase 2 — Authentication (2–3 hrs)

  • Backend: POST /auth/signup (bcrypt hash password, insert User), POST /auth/login (verify, issue JWT), POST /auth/refresh
  • Mobile: Login/Signup screens with Zod-validated forms
  • Store JWT in expo-secure-store, hydrate authStore on app launch
  • Route guard: app/_layout.tsx redirects to (auth)/login if no valid session, else to (tabs)/home
  • Offline rule: if a token exists in SecureStore but there's no internet, still allow entry to the app (don't block on a network validation call)

Done when: you can sign up, get logged out, log back in, force-quit the app, reopen it in airplane mode, and still land on Home (not get bounced to Login).

Phase 3 — Course Library (read-only, online) (2 hrs)

  • Backend: GET /courses, GET /courses/:id
  • Seed 4–5 courses in Postgres (match your earlier mockups: Python Basics, DBMS, Computer Networks, OS, DSA)
  • Mobile: Course Library screen fetches and lists courses; Course Details screen shows lessons/metadata
  • connectivityStore: wire up NetInfo.addEventListener, expose online | lowBandwidth | offline

Done when: courses load live from your backend, and toggling airplane mode flips a visible "Offline" banner without crashing the screen.

Phase 4 — Download Manager (the linchpin) (4–6 hrs)

This is the phase to not rush — everything else depends on it.

  • Backend: GET /courses/:id/pack (metadata + download URL), GET /packs/:id/download (serve a zipped bundle of lesson JSON + any media/PDFs)
  • Mobile downloadManager.ts:
    • Use expo-file-system createDownloadResumable so downloads survive app backgrounding and can resume after connection loss
    • On completion: verify checksum, unzip/write into a per-course directory under FileSystem.documentDirectory
    • Write a row into local SQLite learning_packs with state = ACTIVE, downloaded_at, last_used_at
    • On failure/cancel: discard partial file, keep pack NOT_DOWNLOADED — never leave a half-written pack marked ACTIVE
  • UI: download progress bar on Course Details, "Available Offline" badge once complete

Done when: you can start a download, kill the app mid-download, reopen, and resume/complete it — and the resulting content is readable with Wi-Fi fully off.

Phase 5 — Lesson Viewer (offline read path) (2–3 hrs)

  • Read lesson content straight from local SQLite + FileSystem — zero network calls on this screen once a pack is downloaded
  • Update learning_packs.last_used_at every time a lesson from that pack is opened
  • Mark lesson complete → write to local progress table, enqueue a LessonCompleted sync item (queue logic comes in Phase 7, just write the row for now)

Done when: with airplane mode on, you can open any downloaded course, browse every lesson, and mark one complete, with the UI never showing a loading spinner waiting on network.

Phase 6 — Offline Quiz (3–4 hrs)

  • Local quiz_questions table populated from the downloaded pack
  • Quiz screen: each answer selection writes immediately to local quiz_attempts in progress (not just at submit)
  • Score calculated locally at submit; write final attempt row; enqueue QuizAttemptCreated
  • Kill-test: force-quit mid-quiz after answering 2 of 5 questions, reopen — first 2 answers should still be there

Done when: a full quiz attempt, start to score screen, works with the device in airplane mode, and survives an app kill mid-quiz with no answer loss.

Phase 7 — Sync Engine (3–4 hrs)

  • Backend: POST /sync/batch — accepts an array of queue items, dedupes by client-generated UUID, upserts into the right tables, returns per-item ACK/error
  • Mobile syncEngine.ts:
    • Listens for connectivity restored (NetInfo transition to online)
    • Reads all PENDING rows from sync_queue, sends in a batch
    • On ACK: mark SYNCED. On failure: increment retryCount, exponential backoff, leave PENDING
    • Conflict rule: progress uses max(local, server); quiz attempts/notes are append-only (no conflict possible)
  • UI: SyncBadge component showing "X items pending" / "All synced" / "Syncing..."

Done when: you can go through Phases 5–6 fully offline, then flip Wi-Fi back on, and watch the sync badge go from "3 pending" to "All synced" without touching anything — and confirm the rows actually landed in Postgres.

Phase 8 — Storage Manager & Lifecycle (4–5 hrs)

This is your differentiator — budget real time for it.

  • storageManager.ts: implement the state machine from the design doc — evaluateArchiveEligibility() checks last_used_at against a configurable threshold (use an env/config constant, not a hardcoded 7 * 24 * 60 * 60 * 1000 — you'll want to shrink this for demos)
  • Background check (on app foreground, or a lightweight interval): any ACTIVE pack unused past the threshold → compress/reduce, set state = ARCHIVED, archived_at = now, toast notification
  • ARCHIVED pack unused past the second threshold (45 days, same config pattern) → show CleanupModal (Keep / Delete)
    • Keep → cleanup_decision = KEEP, stay archived, re-check after another 7-day-equivalent window
    • Delete → check syncStatus across that course's progress/attempts/notes; if clean, delete files, state = CLOUD; if not, hold and retry after sync
  • Downloads & Storage screen: list packs grouped by state (Active/Archived/Cloud), storage bar, Restore button (blocked with a message if offline)

Done when: with your debug thresholds set to e.g. 30 seconds / 2 minutes, you can watch a pack go ACTIVE → ARCHIVED → cleanup popup → CLOUD live, restore a CLOUD pack back to ACTIVE, and confirm a pack with an unsynced quiz attempt refuses to fully delete until synced.

Phase 9 — AI Doubt Assistant (3–4 hrs)

  • Backend: POST /ai/ask — forwards to your chosen LLM API with the student's question (+ course context if available)
  • Mobile aiService.ts:
    • If online → call /ai/ask, render answer + source/confidence
    • If offline → simple retrieval over local ai_chunks (even basic keyword/substring matching is fine for a hackathon — you don't need real embeddings unless you have time) → if a relevant chunk is found, answer from it with a source tag; if not, show the explicit "couldn't find enough information" message — never fall through to a generic/fabricated answer
  • Chat UI screen wired to this service instead of the mocked prototype from before

Done when: you can ask the same question with Wi-Fi on (get a real LLM answer) and with Wi-Fi off (get either a sourced local answer or the honest "not enough info" message — never a hallucination).

Phase 10 — Scholarships & Career (2–3 hrs, can simplify)

  • Seed a small scholarships table (4–6 rows) with eligibility_rules as JSON
  • Backend: GET /scholarships?profile=... runs simple rule matching (age/category/course/income thresholds — plain JS conditionals are fine, no need for a rules engine library)
  • Mobile: Scholarship screen shows matches with "why you match" and lastVerifiedAt; cache last successful fetch locally so offline shows stale-but-labeled data
  • Career screen: compute suggested next steps from local progress/quiz_attempts data (can be simple threshold logic: e.g. "if course X complete and course Y not started, recommend Y")

Done when: matches reflect a real (even if simple) rule check against a test profile, and both screens degrade gracefully offline (showing cached/stale data, not a blank error screen).

Phase 11 — Error States & Polish (2–3 hrs)

Go through the error/edge-case matrix from the design doc one row at a time and manually trigger each:

  • Kill Wi-Fi mid-download → confirm resume works
  • Fill device storage (or fake a low-storage check) → confirm blocked download with a clear message
  • Corrupt a pack file manually → confirm checksum failure triggers re-download prompt, not a crash
  • Force a duplicate sync send → confirm backend dedupes cleanly
  • Expire a JWT manually → confirm offline access to downloaded content still works

Also at this stage: consistent OfflineBanner placement across all screens, consistent color/copy for Active/Archived/Cloud states, loading skeletons instead of blank screens.

Done when: nothing in the app shows a raw error, a blank white screen, or an unhandled crash for any case in the matrix.

Phase 12 — Demo Prep (1–2 hrs)

  • Set storage-lifecycle thresholds to demo-friendly values (see Phase 8) via a single config flag you can flip back before judging if asked to show "real" behavior
  • Pre-seed one course as already downloaded and one as not, so the demo doesn't wait on a live download
  • Rehearse the exact 21-step demo flow from the design doc, with a stopwatch — trim anything that runs long
  • Have a fallback: screen-record the full flow once, in case live Wi-Fi/airplane-mode toggling misbehaves during judging
