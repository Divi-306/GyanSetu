GyanSetu — Product & System Workflow Design

"Learning continues, even when connectivity doesn't."

This document defines the product and system design for GyanSetu before any implementation. No application code is included — this is the workflow, architecture, data model, and build plan.

A. Product Workflow (student journey)

Install app → (has internet?) → Sign up / Login → Home
   → Browse Course Library → Open Course Details
   → Download Learning Pack → Study Lessons → Take Quiz
   → Progress saved locally → Ask AI doubts → Check Scholarships
   → Check Career Guidance → (connectivity returns) → Auto-sync → Continue

The loop that matters: Download once → learn indefinitely offline → sync opportunistically. The server is a convenience for freshness and backup, not a dependency for learning.

Why this works: every read/write a student makes during a study session hits SQLite/FileSystem first. The app never blocks a UI action waiting on the network — the network is only consulted for downloads, AI when online, scholarship refresh, and the sync engine's background flush.

C. Offline Workflow

Trigger Behavior
Internet lost mid-session Banner switches to "🔴 Offline Mode"; no modal, no blocking. App keeps running off SQLite/FileSystem.
App opened with no internet, previously logged in JWT read from secure storage; skip network validation; open Home directly using cached profile + local packs.
App opened with no internet, never logged in Show Login screen with explicit "You need internet to sign in the first time" message — do not fake a login.
Feature requiring network is tapped offline Disable the action visually (not hidden) and show inline text: "Requires internet" rather than a dead click or generic error.

Available offline: downloaded lessons/PDFs, offline quizzes, progress tracking, notes, offline AI (on downloaded content only), previously fetched scholarship/career data (marked stale). Unavailable offline: new pack downloads, live sync, online AI, scholarship/career refresh.

D. First-Time Install With No Internet (honesty constraint)

The APK ships a small bundled starter pack (not arbitrary course content):

  • 1 sample lesson, 1 sample quiz (5 questions), app onboarding/help text, a minimal local knowledge chunk set so the AI assistant has something to answer from.

This is explicitly not a substitute for real courses. The app must say, in-UI, on first offline launch: "You're offline. Try the sample lesson below, or connect to the internet to download full courses." No claim of full offline capability before any download has occurred.

E. Connectivity States

Detected via NetInfo + a lightweight bandwidth probe (small ping/latency check or reading NetInfo.details.cellularGeneration / effective type where available).

State Detection Behavior
Online (good) Connected, latency/throughput above threshold Full downloads, sync, online AI, live scholarship/career fetch
Low bandwidth Connected, but slow (2G/3G, high latency, or a failed probe within timeout) Auto-select compressed pack variant, text-prioritized lessons, defer large media, warn before large downloads
Offline Not connected All online-only actions disabled/queued; offline feature set only

State is a single global Zustand store (connectivityStore) read by every screen — no per-screen network checks.

F. Learning Pack Concept & Lifecycle

A Learning Pack = lessons + media/PDFs + quiz questions + metadata + a local AI knowledge slice, versioned per course.

State machine

stateDiagram-v2
    [*] --> NOT_DOWNLOADED
    NOT_DOWNLOADED --> DOWNLOADING: user taps Download
    DOWNLOADING --> ACTIVE: download verified complete
    DOWNLOADING --> NOT_DOWNLOADED: failed / cancelled (partial file discarded)
    ACTIVE --> ACTIVE: used within 7 days (lastUsedAt refreshed)
    ACTIVE --> ARCHIVED: 7 days unused (auto, compressed)
    ARCHIVED --> ACTIVE: user restores (needs internet)
    ARCHIVED --> ARCHIVED: used or kept (resets 7-day sub-timer)
    ARCHIVED --> DELETE_WARNING: 45 days unused since archive
    DELETE_WARNING --> ARCHIVED: user chooses Keep (monitoring continues, re-ask in 7 days)
    DELETE_WARNING --> CLOUD: user chooses Delete AND sync is clean
    DELETE_WARNING --> PENDING_SYNC: user chooses Delete BUT unsynced data exists
    PENDING_SYNC --> CLOUD: sync completes, then content deleted
    CLOUD --> DOWNLOADING: user re-downloads

Key rule encoded above: Delete never fires while unsynced student data exists. It waits in PENDING_SYNC, attempts sync opportunistically, and only removes local content files once the server has acknowledged the student's data.

Content vs. student data (critical separation)

Content data Student data
Examples Lesson text/media/PDFs, quiz question bank Quiz attempts, progress %, notes, sync queue entries
Can be archived/compressed Yes No
Can be deleted (with confirm) Yes, once synced-content is safe to drop Only after server-confirmed sync; never silently
Re-obtainable Yes, re-download from server No — it's the source of truth until synced

G. Storage-Management Workflow

Storage Manager (a dedicated module, not scattered logic) owns: checkAvailableStorage · calcPackSize · trackLastUsedAt · evaluateArchiveEligibility · compress/decompress · showStorageWarnings · checkSyncStatusBeforeDelete · restorePack · deleteContentSafely

Day-by-day policy

  • Day 0–7 (ACTIVE): every open/lesson-view/quiz-attempt on that pack updates lastUsedAt.
  • 7 days unused → ARCHIVED (automatic, no confirmation needed — reversible, non-destructive): content compressed where possible (media re-encoded/removed, text kept), toast: "Python Basics has been archived to save storage." Progress/metadata/sync-state untouched.
  • Restore: if online → re-fetch full pack, verify checksum, mark ACTIVE. If offline → block with "Internet connection is required to restore this learning pack."
  • 45 days unused since archive → DELETE_WARNING (blocking confirmation, destructive path): 
    Storage Cleanup
"You haven't used Python Basics for 45 days."
"It currently uses 75 MB of storage."
[ Keep Pack ]   [ Delete Pack ]
    • Keep → cleanupDecision = KEEP, stays ARCHIVED, monitored; if still unused after another 7 days, re-ask the same dialog (not a silent loop — bounded, user-visible cadence).
    • Delete → run sync-safety check (progress/attempts/notes/pending queue) → if clean, delete local files, state → CLOUD; if not clean, hold in PENDING_SYNC, attempt sync in background, delete content only after ACK.

Storage-aware adaptation

Device storage Behavior
High (plenty free) Offer full-quality pack by default
Limited Default to compressed variant; prioritize text + essential lessons; large media optional/deferred
Critically low Block new downloads; surface Storage Manager recommendations (archive candidates, size breakdown); never auto-delete without confirmation

H. Sync Workflow

Every local mutation that matters (quiz attempt, lesson completed, progress update, note created) is written to SQLite and appended to sync_queue in the same local transaction — the UI never waits on the network to consider an action "saved."

sequenceDiagram
    participant UI
    participant SQLite
    participant Queue as sync_queue
    participant Net as NetInfo
    participant API
    UI->>SQLite: write student data
    UI->>Queue: enqueue {type, payload, status: PENDING}
    UI-->>UI: show "saved locally" (instant)
    Net-->>Queue: connectivity restored (listener)
    Queue->>API: POST batch (oldest first)
    API-->>Queue: 200 ACK / 409 conflict / 5xx error
    alt ACK
        Queue->>Queue: status = SYNCED
    else conflict
        Queue->>Queue: apply resolution rule, status = SYNCED/RESOLVED
    else error
        Queue->>Queue: retryCount++, backoff, status stays PENDING
    end

Conflict rule (kept simple for MVP): last-write-wins per field, by timestamp, except quiz attempts and notes, which are append-only (a new attempt never overwrites a prior one — there's nothing to conflict). Progress percentage uses max(local, server) — a student is never shown regression.

sync_queue item shape: id, type, payload(json), createdAt, retryCount, status(PENDING/SYNCING/SYNCED/FAILED), lastAttemptAt.

I. AI Doubt-Solving Workflow

flowchart TD
    Q[Student question] --> Online{Online?}
    Online -->|Yes| LLM[Backend → LLM/API] --> A1[Answer + source + confidence]
    Online -->|No| RET[Retrieve from downloaded AIKnowledgeChunks]
    RET --> Found{Enough relevant content?}
    Found -->|Yes| A2[Local answer + source + confidence]
    Found -->|No| Hon["'Couldn't find enough info in your\ndownloaded material — connect to\nthe internet for a broader answer.'"]

Non-negotiable: offline mode never hallucinates past its knowledge base. Every answer — online or offline — carries a source tag and a confidence indicator; the local path has a hard "insufficient data" exit instead of guessing.

J. Voice Workflow

Voice input → Speech-to-text → AI processing (online/offline path above) → Answer → Text-to-speech
  • Online: cloud STT/TTS, Hindi + English.
  • Offline: use on-device STT/TTS only where the platform genuinely supports it; if not available, fall back to text input/output with a visible note — never claim cloud voice APIs work with no connection.

K. Offline Quiz Workflow

flowchart TD
    Q1[Show question] --> SEL[Student selects answer]
    SEL --> SAVE[(Write to SQLite immediately)]
    SAVE --> NEXT{More questions?}
    NEXT -->|Yes| Q1
    NEXT -->|No| SCORE[Calculate score locally]
    SCORE --> PROG[Update StudentProgress]
    PROG --> ENQ[Enqueue QuizAttemptCreated in sync_queue]
    ENQ --> LATER[Sync engine flushes when online]

Durability: each answer is a committed SQLite write the instant it's selected (not batched at submit), so app crash, background/kill, or phone restart mid-quiz loses at most the current unselected question — never prior answers. If internet returns mid-quiz, nothing changes UX-wise; the quiz keeps running fully local and syncs only at submit.

L. Scholarship Workflow

flowchart LR
    P[Student profile] --> RULE[Eligibility rules engine]
    DB[(Scholarship DB, server-synced)] --> RULE
    RULE --> MATCH[Matches + 'why you match' breakdown]
    MATCH --> DETAIL[Scholarship details:\nlast updated, source, verification status]
    DETAIL --> LINK[Official application link (external)]

The app never asserts final eligibility — only "you appear to match, based on data last updated X." Scholarship data fetched online only; offline shows last-cached results clearly labeled stale (e.g., "Showing scholarships as of 3 days ago").

M. Career Guidance Workflow

flowchart LR
    IN["Interests + completed courses +\nquiz performance + stated goals"] --> AN[Skill/progress analysis]
    AN --> PATH[Career paths]
    PATH --> NEXT["Explainable next steps\n(e.g. 'You finished Python Basics,\nnow learning DSA → next: SQL, projects')"]

Recommendations are computed from local StudentProgress + QuizAttempt data first (works offline for anything already known), refreshed with server-side career-path data when online.

N. Authentication Workflow

flowchart TD
    SU[Sign Up] --> PROF[Create profile] --> LOG[Login]
    LOG --> JWT[Receive JWT, store in SecureStore]
    JWT --> APP[Authenticated app]
    APP -->|token expired + online| REFRESH[Silent refresh or re-login prompt]
    APP -->|token expired + offline| OFFOK["Allow continued access to\nlocal/offline content;\nblock only server-dependent calls"]
  • Token stored via Expo SecureStore (never AsyncStorage in plaintext).
  • Logout clears token + optionally offers "keep downloaded content" vs. "clear everything" (default: keep content, since it's the student's own device storage).
  • Rule: an expired/missing-refresh token while offline must never lock a returning, previously-authenticated student out of their downloaded courses.

V. Recommended Implementation Order

  1. Foundations: Expo app scaffold + Router + Zustand stores + SQLite schema (§R) — before any feature.
  2. Auth: signup/login/JWT, SecureStore — unblocks everything else.
  3. Course Library + Course Details (read-only, server-backed): prove online fetch works.
  4. Download Manager: real pack download → SQLite + FileSystem write → ACTIVE state. This is the architectural linchpin; get it right before building on top.
  5. Lesson Viewer + offline read path: confirm content renders with zero network calls once downloaded.
  6. Offline Quiz + local commit + sync_queue write: core "learning continues" proof point #1.
  7. Sync Engine: connectivity listener → batch flush → conflict rule. Test by toggling airplane mode repeatedly.
  8. Storage Manager + state machine (Active→Archived→Cloud) + Cleanup popup: your standout differentiator — build with fast debug timers first, tune to real 7/45-day constants last.
  9. AI Doubt Assistant: offline retrieval path first (works without any external dependency), then wire the online LLM path.
  10. Scholarship + Career screens: lowest technical risk, do last, can be simplified per §U without hurting the core narrative.
  11. Polish pass: offline banner consistency, sync status badge, error states from §O — do this only once 1–9 work, since these are cross-cutting and easy to retrofit.

This order front-loads the two things that make GyanSetu not "just an LMS with a download button" — the download/offline pipeline (step 4–6) and the storage lifecycle (step 8) — so if hackathon time runs out, what's missing is scholarships/career polish, not the core thesis.
